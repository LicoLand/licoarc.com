    Nostr compatibility.
    Open collaboration.

    Communicate through a common private-message baseline. Add stronger Endpoint protection and shared collaboration capabilities when both clients support them.

    V1 Candidate definition. This is an independently specified Nostr binding alongside the native Protocol Line, not a claim that LicoUp or another client has already implemented or demonstrated interoperability.

    Two paths, one open ecosystem

    CommunicationCommon requirementsNot required
    Standard private textNIP-01, NIP-17, NIP-44 v2 and NIP-59; NIP-42 when required by a relayLicoArc keys, native Station APIs, federation membership or LicoUp
    Enhanced Endpoint messagesThe Nostr carrier binding, native V1 protection and an approved peer associationAn official client, official relay or the same UI
    Enhanced collaborationAn exact common application definition and local execution authorizationThe same workflow engine or client brand

    Compatibility depends on the shared message specification, not merely on having a Nostr public key. A relay can carry opaque events without understanding their application meaning. Any independent client implementing the common extensions can participate.

    Ordinary Nostr messages stay ordinary

    Standard chat uses kind 14 rumors, kind 13 seals and kind 1059 gift wraps. Recipients publish their private-message relays in kind 10050. Messages follow those relay choices and the upstream NIP-17 format, without LicoArc-only tags or fields.

    LicoUp may organize conversations, extract a task with the user’s approval, or run local workflows without requiring the sender to install a different client. Text is never automatically interpreted as an executable protocol command. Disclosure to a model provider requires separate authorization.

    Enhancements are shared contracts, not a private network

    The enhanced path carries unchanged native LicoArc objects inside NIP-59 wraps. A dedicated inner kind, 44900, and the exact licoarc.v1 namespace identify the extension. The kind is experimental and unallocated upstream; it is not presented as an approved NIP. NIP-78 private app storage is not used as a cross-application interchange.

    Nostr account keys and native Endpoint keys are distinct. After native establishment and authority admission, protected binding messages associate the exact accounts, channel and native session. Capabilities are the intersection of application identifiers and exact definition digests. They do not negotiate cryptographic algorithms or confer permission to execute a tool.

    The carrier uses bounded 8 KiB fragments, preserving native bytes and their tighter type-specific limits. Retries reuse stored bytes. Only authenticated Endpoint confirmations can advance native acceptance or execution finality; relay storage acknowledgments cannot.

    Security is selected per message

    An enhanced operation never silently becomes ordinary chat. Unsupported capabilities, failed binding or unavailable peers produce explicit failure or pending state. No plaintext fallback or weaker compatibility copy is sent. Standard and enhanced conversations can coexist with clear per-message labels.

    NIP-44 does not provide cryptographic forward secrecy, post-compromise recovery or post-quantum protection. Native Endpoint claims retain their own scope and assumptions; they do not automatically prove the new carrier or account binding. Neither path hides all relay metadata, proves deletion by a malicious relay, or establishes that a client’s code is honest.

    What remains in the native Protocol Line?

    The native eight-capability V1 definition remains available. Its HTTPS Transport and Federation Governance apply to that native service, not as requirements for ordinary Nostr clients or relays. Native full-line conformance, Nostr chat interoperability and enhanced application interoperability are separate claims.

    SOURCENative Protocol Line architecture

    Definition checks and implementation evidence

    The binding has its own closed schemas, normative field inventory, deterministic artifact and synthetic conformance corpus. Tests cover classification, framing, resource bounds, account binding, capability matching and explicit path selection. They are not production cryptography or real-client interoperability tests.

    Before claiming runtime support, an implementation must exchange actual standard messages with an independent NIP-17 client and test enhanced sessions, revocation, loss, reordering and restart behavior with independent peers. The general application envelope does not invent task commands: each shared application definition owns its own payload and effect semantics.
